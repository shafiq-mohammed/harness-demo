# T-004: Link expiry

Status: todo
Depends on: T-003

## Goal
A link can be created with an `expires_at` timestamp; once that time passes, `/<code>` stops redirecting and answers 410 Gone.

## Scope
In:
- `expires_at` field on `CreateLinkRequest` (optional, tz-aware, strictly in the future per the injected clock).
- 410 `link_expired` branch on `GET /{code}` with no hit increment.
- `expires_at` populated in `LinkOut` for create and `GET /links/{code}`.
Out:
- Deleting or purging expired links, TTL-based deletion in storage.
- Extending or editing expiry after creation.
- Relative `ttl_seconds` input (absolute timestamp only).

- `POST /links` (changed; header `X-API-Key` required)
  - Request: `{"url": "https://example.com", "expires_at": "2026-01-02T00:00:00+00:00"}` (`expires_at` optional)
  - 201: `LinkOut` with `expires_at` echoed, serialised in UTC (e.g. `"2026-01-02T00:00:00Z"`); null when omitted.
  - 422 `validation_error` if `expires_at` is naive (no offset), unparseable, or not strictly greater
    than `clock.now()` (message `"expires_at must be in the future"`).
- `GET /{code}` (changed, no auth)
  - 410 `{"error": "link_expired", "message": "..."}` when `link.is_expired(clock.now())`; `hit_count` unchanged.
  - Otherwise 302 + increment as in T-003. 404 for unknown codes unchanged.
- `GET /links/{code}` unchanged: expired links remain readable with their `expires_at`.

## Acceptance criteria
AC1. Given the clock is at T0 When `POST /links` is sent with a valid key, a valid URL and `expires_at` = T0 + 1 hour (with a `+00:00` offset) Then the response is 201 and `expires_at` parsed with `datetime.fromisoformat` equals T0 + 1 hour; and a request without `expires_at` still returns 201 with `expires_at` null.
AC2. Given the clock is at T0 When `POST /links` is sent with `expires_at` equal to T0, or T0 - 1 second, or a naive timestamp `"2026-01-01T13:00:00"`, or `"not-a-date"` Then each response is 422 with `error == "validation_error"`, never a 500.
AC3. Given a link with `expires_at` = T0 + 1 hour and the clock at T0 When `GET /{code}` is requested Then the response is 302 with the correct `Location`, and `hit_count` becomes 1.
AC4. Given the same link When the clock is advanced to exactly T0 + 1 hour (via `clock.set`) and `GET /{code}` is requested Then the response is 410 with `error == "link_expired"` and `GET /links/{code}` still reports the `hit_count` from before (1) with the original `expires_at`.
AC5. Given a link created without `expires_at` When the clock is advanced by 10 years and `GET /{code}` is requested Then the response is still 302.
